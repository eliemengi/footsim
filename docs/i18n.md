# FootSim – Internationalisierung (i18n)

Erstellt: Phase 2.1  
Gilt ab: footsim-v8

---

## Warum diese Architektur

FootSim benötigt ein i18n-System, das:

- ohne Backend-Roundtrip funktioniert (PWA, Offline-Betrieb)
- keine externe Abhängigkeit einführt
- beliebig viele Sprachen aufnehmen kann ohne Strukturänderung
- mit Vanilla JS und Jinja2 kompatibel ist
- den Service Worker nicht kompliziert

Deshalb wurde **clientseitiges JSON-Wörterbuch** gewählt.

### Verworfene Alternativen

| Ansatz | Warum verworfen |
|---|---|
| Flask-Babel (serverseitig) | Jeder Sprachwechsel = neuer HTTP-Request; bricht Offline-Funktion |
| i18next-Library | Overkill für Vanilla-JS-Projekt; unnötige Abhängigkeit |
| `if (lang === "en")` direkt im Code | Nicht wartbar; bei 10 Sprachen unkontrollierbar |
| Hardcodierte Strings belassen | Keine nachträgliche Übersetzung möglich ohne Gesamtumbau |

---

## Architektur

```
static/
  i18n/
    de.json   ← Deutsch (Standard, immer vollständig)
    en.json   ← Englisch
    (pt.json) ← Portugiesisch, später
    (fr.json) ← Französisch, später
```

Beim Start lädt `script.js` die passende Sprachdatei per `fetch()`.  
Eine globale `t(key)` Funktion gibt den übersetzten String zurück.  
Fehlt ein Schlüssel, fällt `t()` auf Deutsch zurück.

---

## Schlüsselkonventionen

### Namensschema

```
bereich.unterbereich.bezeichnung
```

Alle Schlüssel: **lowercase**, **Englisch**, **Punkte als Trennzeichen**.

### Präfixe

| Präfix | Bereich |
|---|---|
| `nav.*` | Hauptnavigation (vier Bereiche) |
| `hero.*` | Hero-Bereich auf der Startseite |
| `season.*` | Saisonauswahl |
| `competition.*` | Wettbewerbs-Auswahl und Status |
| `matchday.*` | Spieltag-Auswahl |
| `tab.*` | Tabs im Output-Panel |
| `table.*` | Tabellen-Ansicht |
| `scorers.*` | Torjäger-Ansicht |
| `fixtures.*` | Spiele-Ansicht |
| `sim.*` | Spielsimulation |
| `season_sim.*` | Saisonsimulation |
| `compare.*` | Ligavergleich |
| `transfers.*` | Transfervergleich |
| `players.*` | Spielervergleich (Platzhalter) |
| `cl.*` | Champions-League-spezifisch |
| `settings.*` | Einstellungs-Drawer |
| `status.*` | Status-Meldungen (Laden, Fehler, Erfolg) |
| `error.*` | Fehlermeldungen |
| `legend.*` | Tabellenlegende |

### Strings mit Variablen

Variablen werden mit `{variablenname}` in geschweiften Klammern markiert:

```json
"competition.selected": "{name} gewählt",
"sim.top_score_count": "{count} von allen Simulationen"
```

`t()` ersetzt sie per einfachem String-Replace:

```javascript
t("competition.selected", { name: "Bundesliga" })
// → "Bundesliga gewählt"
```

### Was NICHT in i18n gehört

- Vereinsnamen (kommen von der API)
- Spielernamen (kommen von der API)
- Saison-Labels (kommen von der API)
- Wettbewerbsnamen (kommen von der API)
- CSS-Klassen, IDs, technische Strings

## Implementierung

### `t()` Funktion (in `script.js`)

```javascript
let _translations = {};
let _fallback = {};

async function loadTranslations(lang) {
    try {
        const res = await fetch(`/static/i18n/${lang}.json`);
        _translations = await res.json();
    } catch {
        _translations = {};
    }
    if (lang !== "de") {
        try {
            const res = await fetch("/static/i18n/de.json");
            _fallback = await res.json();
        } catch {
            _fallback = {};
        }
    } else {
        _fallback = {};
    }
}

function t(key, vars = {}) {
    let str = _translations[key] ?? _fallback[key] ?? key;
    for (const [k, v] of Object.entries(vars)) {
        str = str.replaceAll(`{${k}}`, v);
    }
    return str;
}
```

Fehlt ein Schlüssel: Fallback auf Deutsch. Fehlt er auch dort: Schlüssel selbst als String zurückgeben. So bleibt die App nie leer.

### Sprachauswahl

Reihenfolge der Priorität:

1. Explizite Nutzerauswahl (wird in `localStorage` gespeichert, Schlüssel: `footsim_lang`)
2. Browser-Sprache (`navigator.language`)
3. Standard: `de`

---

## Eine neue Sprache hinzufügen

1. `static/i18n/de.json` kopieren → `static/i18n/pt.json`
2. Alle Werte ins Portugiesische übersetzen (Schlüssel bleiben auf Englisch)
3. Im Einstellungs-Drawer den neuen Sprach-Button ergänzen
4. Fertig – kein weiterer Code-Eingriff nötig

### Fehlende Schlüssel in neuer Sprache

Fehlende Einträge fallen automatisch auf Deutsch zurück. Das System bleibt nutzbar, auch wenn eine Übersetzung noch unvollständig ist.

---

## Regeln die nicht verletzt werden dürfen

1. **Kein neuer sichtbarer UI-Text direkt im HTML oder JS** – immer über `t()`
2. **Schlüssel immer auf Englisch**, Werte in der jeweiligen Sprache
3. **`de.json` ist immer vollständig** – sie ist die Fallback-Basis für alle anderen Sprachen
4. **Variablen immer mit `{name}`**, nie mit String-Konkatenation im Schlüsselwert
5. **API-Daten werden nie in i18n-Schlüsseln verpackt** – sie kommen direkt vom Backend
6. **Ein Schlüssel, eine Bedeutung** – nie denselben Schlüssel für zwei verschiedene Kontexte recyceln
